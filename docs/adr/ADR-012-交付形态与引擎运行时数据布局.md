# ADR-012: 交付形态与引擎运行时数据布局

- 状态: 已接受。决策 **1、2、3、4、5、8 已实现**并经容器正/反向验证（见三条「验证结果」
  小节与「门禁 3+4 验证结果」）；决策 6 的评审红线尚未写进 `AGENTS.md`，决策 7 待随
  安装说明落地。
- 日期: 2026-09-14
- 决策者: 龚成
- 相关: ADR-001（引擎可插拔）、ADR-011（guizang 运行时归位）、
  `docs/research/2026-09-14-容器化可行性.md`（本 ADR 全部证据的出处所在）

## 背景

要把系统打包成可安装到 Linux 的软件。体检发现：**容器化本身不难，难在两个输出引擎的
"运行时数据布局"长期不统一**，而这个不统一在过去只是开发机的不便，到了交付现场变成阻塞。

三套可写路径只有一套受部署变量控制：guizang 产物走 `DECKSMITH_JOBS_ROOT`；SQLite 走
`DATABASE_URL`（`.env` 未设）；**ppt_master 产物硬落在 `lib/ppt-master/projects/`**，
即上游只读副本内部（AGENTS 规则 4）。

### 口径演化（如实记录，含被推翻的部分）

本 ADR 在讨论中经过三轮收窄，前两轮的结论被第三轮推翻：

1. 第一轮曾倾向"上游契约改不动，只能部署期打补丁"：即把 `lib/ppt-master/projects/` 换成
   指向数据卷的软链（下称 **B 方案**）。该方案已完成可行性验证——上游 0 个硬性阻断点，
   我方 glob/`is_dir`/`st_mtime` 实测均穿透软链（见调研文档 1.1）。
2. 同轮决定"产物落点先只记 ADR、零代码改动"。
3. **第三轮由决策者推翻前两条**：要求 ppt_master 与 guizang 一样，**在运行时由调用方指定
   写入位置**。B 方案与"只记 ADR"因此**降级为兜底路径**，不再是主方案。

推翻后补做的核查（决定了本 ADR 决策 1 是否成立）：

- 上游产物根有**两套来源**：`project_management/cli.py:233` 用 `Path.cwd() / "projects"`
  （决定 `init` 把项目建在哪）；`project_management/paths.py:19-23` 的 `PROJECTS_ROOT`
  由 `__file__` 反推（与 cwd 无关）。今天两者相等，纯属 `cwd` 恰好设成 `lib/ppt-master/`。
- 分裂的后果已定位：`PROJECTS_ROOT` 的全部消费者是 `cli.py:854`（源材料 move/copy 判定）
  与 `cli.py:1027`（源目录清理）。**我方传入的源文件从来不在 `projects/` 之下，今天走的
  就是 copy 分支**，故改 `cwd` 不改变其行为。
- 结论：把 `cwd` 改为任务目录，在现有上游代码下**不会引入硬失败**，且顺带解决串页隐患
  （见决策 1 第 3 点）。

## 决策

### 1. ppt_master 产物落点归位到任务目录

- `cwd` 从 `lib/ppt-master/` 改为 `<jobs_root>/<job_id>/`，与 ADR-011 决策 3 对齐：
  技能目录只读，agent 不得往其中写产物。
- **订正（本 ADR 初稿写错过的一处判断）**：初稿称"只改我方传给子进程的 `cwd`"。
  实际不止一处——**ppt_master 的技能发现本来就寄生在 `cwd` 上**（claude 启动于技能仓库内，
  自动读到该目录的 `AGENTS.md`）。`cwd` 一改，这条链路即断开，而 `_build_prompt`
  内**没有任何技能路径指令**，任务会静默退化成"agent 凭感觉做 PPT"。
  故必须同时把运行锚点显式写进 prompt（与 guizang 同构）。**这个耦合正是"cwd 既管产物落点、
  又管技能发现"造成的**，也是本 ADR 决策 2 要抽钩子的直接动因。
- 实际改动（`packages/engine/impl/ppt_master/engine.py`，均在我方引擎内，上游仍是一字未改）：
  1. `submit` 的 `cwd=str(job_dir)`；
  2. 新增 `_runtime_anchor(job_dir)`，产出「技能仓库绝对根 + 必读 `AGENTS.md`/`SKILL.md` +
     脚本调用一律绝对路径且不得 `cd` 进子目录 + 产物只写 cwd 下 `projects/`」四段约束，
     追加到 prompt 末尾；
  3. 产物搜索根改为 `_project_roots()`：**任务目录优先、`lib/ppt-master` 兜底**（历史任务可读）。
- **两级搜索根不得混合比较 mtime**：否则新任务的产物可能与历史目录争"最新"，
  把刚消除的串页风险原地请回来。实现为按根顺序查找、高优先级根一有结果即 `break`。
- 产物落点：`<jobs_root>/<job_id>/projects/<题>_<日期>/`。
- 连带收益：定位产物从"按 mtime 猜最新目录"（`engine.py` 三处启发式）退化为确定性查找，
  `job.json` 里 pin `svg_output_dir` 那套防串页机制由兜底降为冗余保险。**这根治了历史上
  "冒领旧任务产物"那类 bug 的成因**。
- **`lib/ppt-master/projects/` 下已有的历史项目不迁移**：它们属于归位前的旧口径，
  迁移需要同时改 `job.json` 里 pin 的路径，收益不抵风险。历史任务继续可读，新任务走新口径。

### 2. 协议新增"运行时准备"钩子，收编引擎各自的部署前置条件

各引擎的**任务生命周期**由 ADR-001 的协议统一，但**运行前置条件**完全散着：guizang 要建
技能软链（`impl/guizang_ppt/engine.py:97`），ppt_master 要有可写的 HOME 与工具目录。
容器化时每加一个引擎就得在 entrypoint 里手写一段针对性处理——这是决策者点名要消除的
"以后又要调理"。

- `packages/engine/core/protocol.py` 增加可选钩子（鸭子类型，与 `get_pages` 同风格，
  **不按引擎名门控**）：`prepare_runtime(job_dir: Path) -> str | None`，语义为"备齐本引擎
  跑一个任务所需的前置条件，返回人类可读的告警或 None"。
- 幂等性由引擎自己保证（`ensure_skill_installed()` 已是此形状，直接纳入该钩子）。
- 调用方（后端启动或 entrypoint）遍历注册表逐个调用，**不出现任何 `if engine_name == ...`**。
- 契约先行：先在 `docs/contracts/engine.schema.json` 的 `OutputEngine` 侧登记该能力，
  再改 `protocol.py`，再改两个引擎。

### 3. 产物落点暂不入协议，以纪律 + 测试约束（承接背景第 2 轮被推翻后的残余部分）

决策 1 是**逐引擎修**，不是**契约上禁止再犯**。本次不做，理由：落点契约一旦进协议，
就得同时定义"谁分配目录、引擎能否再建子结构、多产物如何声明主产物"，属另一轮设计。

- 折中做法：在 ADR 与 `AGENTS.md` 记为**新引擎硬性约定**——产物必须落在调用方分配的
  `job_dir` 之内，不得写入 `lib/`。
- 并留一条**契约测试断言**（根 `tests/contract`）：任一输出引擎跑完任务，
  `result()` 与 `get_pages()` 返回路径必须 `is_relative_to(jobs_root)`。
  这条测试是新引擎的机制保护，取代口头约定。
- 前向兼容：将来若要升级为契约，`prepare_runtime(job_dir)` 的入参就是天然落点，
  不必再改签名。

### 4. 交付形态：Docker Compose，2 服务 + 4 数据卷

| 服务 | 内容 |
|---|---|
| `app` | 后端 + engine 包 + `claude` CLI + Node + `lib/` 技能内容 |
| `web` | Next standalone，`BACKEND_PORT` 必须与 `app` 监听端口同值 |

| 卷 | 承载 | 由什么变量指过去 |
|---|---|---|
| `./data/jobs` | 两引擎产物 + `job.json` + `run.log` | `DECKSMITH_JOBS_ROOT` |
| `./data/db` | SQLite | `DATABASE_URL` |
| `./data/home` | `~/.claude`（技能软链 + 会话 jsonl）与 `~/.ppt-master` | `HOME` |
| `./data/decks` | **仅**归位前的历史产物 | — |

- 密钥（`ANTHROPIC_API_KEY`、`ANTHROPIC_BASE_URL`、`ANTHROPIC_MODEL`）**运行时注入，
  绝不进镜像层**。
- **`HOME` 而非 `CLAUDE_CONFIG_DIR` 是主手段**：上游有 `Path.home() / '.ppt-master'`
  （`scripts/config.py:53`，且读写其下 `.env`）与 `svg_to_pptx/text_outline.py` 两处，
  三者均无重定位开关、又属只读上游不可改码，只有重定向 `HOME` 能一次兜住。
  `CLAUDE_CONFIG_DIR` 降为可选隔离手段，二者不并列使用。
- 历史产物卷（`data/decks`）随旧任务消亡可摘除；届时 4 卷降为 3 卷。

### 5. 技能软链一律启动期现建，禁止携带开发机 `~/.claude`

软链存的是绝对路径。镜像层里烤不进宿主机路径，把开发机 `~/.claude` 挂成卷更会直接断链。
故 `prepare_runtime()`（决策 2）在容器每次启动时按容器内实际路径幂等重建。

### 6. 路径归属比较一律两侧 `resolve()`，列为评审红线

B 方案实测（调研文档 1.1）证明：`Path.glob` 穿透软链，但 `resolve()` 会把它打回真实根，
`a.relative_to(b)` 两侧解析状态不一致时**当场 ValueError**。后端
`service/jobs.py:272-274`、`:319-324` 的"双保险"写法是正确范式。此为防回归约束，非现状缺陷。

### 7. 出网与凭证写进安装说明前置条件第一条

两引擎均硬依赖 `claude` CLI + 出网 + Node，**无离线退路**（ADR-011 决策 2 已确认不保留
纯 Python 兜底实现）。内网客户必须有可达的 Anthropic 兼容网关或代理，否则产品不可用。

### 8. 镜像内解释器唯一：`PATH` 上的 `python3` 必须就是应用解释器

门禁 2 实测发现本机存在**两个解释器分裂**：

- `impl/ppt_master/engine.py:231` 用 `sys.executable`（= `.venv/bin/python`，装了上游技能全树）
  跑 `source_to_md.py`；
- 而 claude 子进程按 **`PATH` 上的 `python3`** 调技能脚本（本机解析到
  `/Library/Frameworks/.../3.14/bin/python3`），**该解释器缺 `skia-pathops`**。

即同一个技能的两条调用路径走的是两套包。本机之所以没炸，只是因为唯一用到 `pathops` 的
`svg_to_pptx/shape_boolean.py` 在本次 3 页任务里没被触发。**这是潜伏故障，不可依赖侥幸。**

- 口径：**整张镜像只有一个 Python 环境**。安装后把该 venv 的 `bin` 置于 `PATH` 首位，
  使 `python3` 与 `sys.executable` 指向同一解释器；不在镜像里另装系统 Python 包。
- 校验：构建期断言 `python3 -c "import pathops, pptx, fitz, mammoth"` 通过
  （即门禁 2 的净空环境检查，直接固化进 Dockerfile）。

## 后果

**正面**

- 三套可写路径收敛为两套可配置路径（产物 → `jobs_root`，库 → `DATABASE_URL`），
  `lib/` 恢复为纯只读，AGENTS 规则 4 从"纪律"变回"事实"。
- 新增引擎的部署成本从"每次补 entrypoint"降为"实现 `prepare_runtime` 即自动接入"。
- 串页/冒领旧产物这类 bug 的成因被结构性移除，不再依赖 pin 机制兜底。
- 交付不再依赖开发机现场：`data/` 四个目录即全部状态，备份与迁移口径清晰。

**代价**

- 决策 1 的落点风险**已由门禁 1 真跑关闭**（产物确实落 `<job>/projects/`）。若后续回归导致
  产物回到 `lib/ppt-master/projects/`，则退回 B 方案（软链，可行性已单独验证）。
- `lib/ppt-master/projects/` 的历史产物与新产物分处两地，演示文件库需兼容两种根。
- `prepare_runtime` 进协议 = 契约、`protocol.py`、两个引擎、entrypoint 四层联动，
  违反"最小改动"直觉；但它消除的是每加一引擎就复现一次的样板。
- 依赖声明已不再是阻塞项（门禁 2 通过）。遗留的是 `factory.py` 那套按名字的 if 分支
  同时违反 ADR-001 第 4 条，与 `registry.py` 的 `_ENGINE_CLASSES` 构成重复知识源——
  **本 ADR 不解决，另案**。

## 门禁 2 验证结果（2026-09-14 依赖清单）

产出三份清单，`packages/backend/requirements.txt` 为**单一安装入口**：

```
backend/requirements.txt      直接依赖 6 项 + -r ../engine/requirements.txt
  └─ engine/requirements.txt  自身零声明 + -r ../../lib/ppt-master/requirements.txt
       └─ 上游 skill 依赖树    只读引用，不复制不改写（AGENTS 规则 4）
backend/requirements-dev.txt  -r requirements.txt + pytest + httpx
```

分层依据是**AST 扫描顶层 import**（不照抄 freeze，freeze 混有传递依赖与无关包）：

- **`packages/engine` 第三方 import 为零**，纯标准库。但它确实需要上游技能全树——
  因为 `engine.py:231` 用 `sys.executable` 在本进程跑 `source_to_md.py`。故 engine 的
  清单只有一条 `-r`，这条非直觉的边已写成注释，避免后人误删。
- backend 只有 4 项是 import 可见的（`fastapi`/`pydantic`/`sqlalchemy`/`pptx`），另有两项
  **扫描扫不出但确属运行时必需**：`python-multipart`（`routes.py:58` 的 `File(...)` 依赖它）、
  `uvicorn`（只在启动命令里，不被 import）。`httpx` 同理是被 `TestClient` 间接需要。
- 只钉直接依赖、传递依赖交 pip：本机 freeze 是 macOS arm64 结果，整表照抄到 Linux 必炸。
- 同时修掉 `packages/engine/pyproject.toml` 的失真声明（缺 `package-dir` 映射、漏
  `engine.impl.guizang_ppt`），并在两个 pyproject 里注明**依赖以 requirements 为唯一事实源**，
  防止长出第二份清单口径。

### 撞出来的两个新发现（都不是读代码能推知的）

1. **契约生成物必须构建期生成，否则前端根本编不出来。**
   `packages/shared/types/` 按规则 7 不入库，`next build` 的 tsc 阶段因此报
   `Cannot find module 'shared-types/api'`。开发机能编译，只因本地残留上次生成结果。
   处置：web 镜像 build 阶段跑 `scripts/generate-types.sh`，并把生成物**同时加入
   `.dockerignore`**——否则开发机残留会被悄悄烤进镜像、还可能带进过期类型。

2. **`requires-python = ">=3.11"` 此前是假声明。** 按 3.11 构建后后端 import 期即崩：
   `TypeError: 'function' object is not subscriptable`。根因是 `ProjectRepo` 定义了名为
   `list` 的方法，同类中更靠后方法的注解 `list[str]` 在类作用域解析到那个方法对象而非内建类型。
   开发机 Python 3.14 因注解默认惰性求值（PEP 649）把它完全掩盖了。
   处置：`repository/jobs.py`、`service/jobs.py` 各加 `from __future__ import annotations`，
   令 3.11/3.12/3.14 行为一致。**把镜像顶到 3.14 迁就现状是更糟的选择**：等于把掩盖问题的
   解释器版本写进交付物，且轮子风险未验。
