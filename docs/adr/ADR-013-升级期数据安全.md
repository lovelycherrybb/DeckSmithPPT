# ADR-013: 升级期数据安全

- 状态: 已接受，**已实现并验证**（决策 1-4 全部落地，见「验证结果」）
- 日期: 2026-09-16
- 决策者: 龚成
- 相关: ADR-003（SQLAlchemy/SQLite）、ADR-012（交付形态与数据布局）、
  `docs/research/2026-09-16-升级数据安全与迁移原子性.md`（本 ADR 全部证据的出处所在）

## 背景

系统按“镜像无状态 + 全部状态落 bind 卷”交付（ADR-012），换镜像不动数据，因此升级本身
不会删数据——这已被真机时间戳与交付包 sha256 三方比对证实。但盘点时发现风险不在“升级删数据”，
而在**程序启动时自动执行的库结构迁移**：

1. 旧实现“列改名后整表搬家”走 `DROP TABLE` → `CREATE TABLE` → 回插，且未包事务。
   Python `sqlite3` 的 legacy 模式会在 DDL 前隐式提交，实测（开发机 3.14、容器 3.11.2 各一次）
   “DROP 之后崩溃”的结果是**表还在、数据 0 行**。
2. 同一处只发 `CreateTable`，索引随旧表被 DROP 后再没建回来，唯一约束静默消失。
3. 迁移改结构前没有任何备份，客户库一旦搬坏无从回退。
4. 镜像回滚（新库 + 旧程序）时，旧程序会照跑迁移，可能把新结构改坏。

升级是客户环境里必然发生、且运维只会按文档敲一条命令的场景，因此这四条都属于交付级缺陷。

## 决策

**一、迁移前先拍库，一次版本跃迁最多一份。** 用 SQLite 在线备份接口（不用文件复制，
避免 WAL 与写入中间态）拍到 `deploy/data/db/backup/`，文件名 `decksmith-v<起>-to-v<止>-pre-upgrade-<UTC>.db`。
已存在同前缀即复用，不覆盖、不堆叠、**不自动删**——清理责任归运维。

**二、整轮迁移跑在一个显式事务里，搬家顺序改成可回滚的顺序。** 把重建表拆成
“建 `<表>__new` → 回插 → 行数校验相等 → `DROP` 旧表 → `RENAME`”，外面套
`BEGIN IMMEDIATE` … `COMMIT`，异常一律 `ROLLBACK`。临时表 DDL 由模型生成
（模型是表结构的唯一事实来源），跨表外键需把被引用表一并复制进临时 metadata 才能编译。
索引在换名后按模型 `__table__.indexes` 重建。

**三、库结构版本写进 `PRAGMA user_version`，作用是记录现状与降级保护，不是迁移开关。**
迁移步骤本身继续按“缺什么补什么”幂等判定——老库可能来自任意历史版本，不能假设它恰好是上一版。
版本号的两个用途：诊断时知道库在哪一版；当**库版本高于程序版本**（回滚旧镜像的典型场景）时
拒绝执行任何结构变更、只告警，把处置权交回运维。

**四、升级固化为 `scripts/upgrade.sh`，顺序为“先备镜像 → 停服务 → 备份 data/ → 换 IMAGE_TAG → 起 → 验健康”。**
先备镜像是硬要求：镜像不存在就先把服务停了，等于把一次失败的升级变成一次停机（本 ADR 起草过程中
就误伤过一次）。离线交付目录显式传入却没有匹配 tar 时**直接失败，绝不静默回退到源码构建**。
`--check` 停在“镜像已备好”，供复验而不制造停机。交付包由 `release.sh` 附带 `ops/`
（compose、`.env.example`、`upgrade.sh`、部署文档），结构刻意与仓库一致，避免运维自己猜文件放哪。

## 后果

**一、迁移失败不再等于丢数据。** 代价是启动期多一次全库快照（体积约等于库大小，本系统库在
百 KB 量级，可忽略），以及备份文件需要运维定期清退。

**二、表结构搬家从“两步不可逆”变成“要么全成、要么原样”，但迁移仍不可回退语义。**
即新版加上的列，退回旧版后旧版读不到——所以回滚必须连同 `data/` 一起解回，文档与脚本输出
都按这个口径写。

**三、`user_version` 成为新的隐性契约。** 今后改动表/列语义必须同步升 `SCHEMA_VERSION`；
只加可空列不必升号（由 `_MIGRATIONS` 幂等兜住）。这条需要靠单测与评审守住。

**四、升级路径只剩一条。** 好处是“先备份”不再依赖运维自觉；代价是 `upgrade.sh` 本身成了
必须维护的交付物，且只能覆盖 bind 卷 + compose 这一种交付形态。

## 验证结果

| 项 | 手段 | 结果 |
|---|---|---|
| 崩溃原子性 | 单测在“旧表已 DROP、新表未提交”处注入异常 | 抛错回滚：旧表与两行数据原样、无 `__new` 残留、`user_version` 未推进；随后仍可正常升上去 |
| 索引回归 | 单测验 `PRAGMA index_list('projects')` 含唯一索引 | 通过（旧实现在此断言下会失败） |
| 数据搬家 | 单测 + `init_db()` 入口跑真·旧库（0.1.x 形态） | 行数不少，`name`→`project_name`、`filename/format/path`→`file_name/file_format/file_path` 值保住，外键子句保住，`user_version` = 2 |
| 备份语义 | 单测验“落一份、内容是升级前原貌、重复运行不堆叠” | 通过；全新库不产生备份 |
| 降级保护 | 单测把库版本设为 99 | 拒改结构、`applied` 为空、不产备份 |
| 冷启动 | 空目录连调两次 `init_db()` | 建表成功、`user_version` = 2、无备份目录、幂等 |
| 脚本安全 | 缺参数 / 交付目录无匹配 tar / `--check` 三条路径 | 分别 exit 2、exit 1（明确提示核对版本与架构）、导入两张 0.2.2 tar 后退出且**未停服务、未改 `.env`** |
| 无回归 | `packages/backend/tests` + `tests/contract` 51 例、`packages/engine` 15 例 | 全绿 |

实测过程中顺手查实的一条附带结论：`docker compose down --volumes` 不会删除 bind 卷对应的宿主目录
（一次性 compose 项目实测，文件仍在），已写进部署文档第七节，取代原先含糊的说法。
