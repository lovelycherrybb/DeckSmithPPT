# ADR-019: 任务调度循环——单线程认领 + DB 状态权威 + 终态先到先得

- 状态: 已接受（本批实现后端，前端判定口径另批）
- 日期: 2026-09-28
- 决策者: 龚成
- 相关: ADR-001（引擎可插拔 / 能力位按钩子派生）、ADR-003（技术栈）、ADR-016（token 口径）、
  **ADR-018（本 ADR 依赖它的 `queued`/`cancelled` 与分层枚举）**、
  `docs/vc_design/states/01-任务状态-TaskStatus.md`

## 背景

ADR-018 记录了两件事的成因，本 ADR 解决它们。补充三条实测事实：

1. **40 线程墙是真的**。`submit()` 用 FastAPI 的 `BackgroundTasks` 挂一个同步的
   `_poll_until_done`，每 15 秒醒一次、最长占 3600 秒，全程独占一条线程；而所有路由也都是同步
   `def`，与它共用 anyio 默认 **40-token** 线程池。用同构最小服务实测：约 **36 个运行中任务**之后，
   新提交要等 29.8 秒才返回，连一个不碰磁盘不碰库的只读接口也要 29.5 秒——是整站冻结，不是降级。
2. **没有任何并发闸**。全仓库搜不到 semaphore / quota / 限流。提交即 `running`、即 fork `claude`
   子进程（每个几百 MB 的 Node 进程 + 一整条 agent 工作流 + 走第三方网关的配额）。
3. **状态的所有权在线程里，所以重启即产生幽灵**。轮询线程随进程消失后没有任何兜底扫描，
   DB 永久停在 `running`；`ppt_master` 引擎连"超时杀进程"都没实现（只有 guizang 的 supervisor 会 kill），
   于是"库说超时了、claude 还在跑还在烧额度"。线上库已有一条被人工标记的
   "引擎进程约 47 小时无输出、supervisor_pid 为空"记录就是这件事的实物证据。

## 决策

### 决策 1：一条专职调度线程取代"每任务一条轮询线程"

```
HTTP 请求线程：校验 → 入库(queued) → 409 粗闸 → 202 返回        （不再挂 BackgroundTasks）
调度线程（lifespan 起、单条 daemon）每拍：
   ① 收尸/接管 → ② 认领（受闸门约束）→ ③ 轮询引擎态 → ④ 超时/收割终态 → ⑤ sleep
```

不选 asyncio 常驻任务：`engine.submit`（fork 子进程）与 `engine.status`（`ps` 探测）都是阻塞调用，
塞回 `run_in_threadpool` 仍然要过那 40 个 token。不选 Celery/RQ/APScheduler：为一个单机 SQLite 应用
加三件套外部依赖。**一条线程 + DB 里的状态**是最小能真正解决问题的形态，且与仓库现状同风格
（`pump`/`supervisor` 本来就是 daemon 线程）。

副产品：认领与轮询集中在一条线程里，**并发闸不需要信号量**——闸门值就是 DB 里 `status='running'`
的行数，重启不丢、跨进程可见。

### 决策 2：引擎 fork 从请求线程搬进调度器

`submit()` 在请求里只做校验与入库，`engine.submit()`（含 `prepare_runtime` 探测、写 draft.md/prompt.md、
fork claude）全部由调度器在认领阶段执行。

**这是并发闸能成立的前提**：不搬的话，用户瞬间提交 50 个就会立刻拉起 50 个子进程，闸门形同虚设。

**已确认接受的代价**：`claude CLI 缺失`这类硬缺失，从"提交瞬间红一条"变成"提交成功、数秒后转 failed"。
理由是提交该快、失败该由执行方报告；且 `entrypoint.sh` 仍在容器启动期用同一个 `prepare_runtime`
入口按退出码拒绝启动，第一道防线没撤。

草稿引擎任务内部那条 `_run_draft_extract` 线程**保留**——引擎自己拥着自己的并发形态，调度器不插手，
避免把"秒级的 source_to_md 转换"塞进认领循环里拖慢整拍。

### 决策 3：认领必须与"进入 running"分开，用 `claimed_by`/`claimed_at` 预留槽位

契约把 `queued` 定义为"引擎子进程尚未 fork 成功"，所以**不能先置 running 再 fork**，否则 fork 失败的行
会冒充 running。做法是两段式：

1. CAS 预留：`UPDATE ... SET claimed_by=:who, claimed_at=:now WHERE status='queued' AND claimed_by IS NULL`
   （status 仍是 queued，槽位已被这只狗占住）
2. fork 成功后 CAS：`queued AND claimed_by=:who → running`，并写 `started_at`

两处 CAS 都**必须**以 `rowcount` 判定胜负，禁止"先 SELECT 再 UPDATE"（TOCTOU）。

第 2 步 `rowcount=0` 的情况**不是异常，而是撤销赢了**：此时必须回收刚 fork 出来的子进程
（调 `engine.cancel`），否则就是"库里已 cancelled、claude 还在跑"的新僵尸。这条是本设计最容易写错的地方。

崩溃遗留的 `claimed_by`（queued 但被占住、超过宽限期）由收尸阶段按证据判定：job.json 里有活 pid
或有产物 → 说明 fork 真的发生过了 → 提升为 running 接管；否则清掉占位、重新排队。

### 决策 4：所有状态写入一律带前置条件，终态先到先得

`UPDATE jobs SET status=? WHERE job_id=? AND status=?`，抢不到（`rowcount=0`）就重读、放弃覆盖，
绝不无条件覆写。于是下面这些竞态都有确定答案，不需要任何锁：

| 竞态 | 结果 |
|---|---|
| 用户撤队 vs 调度器刚 fork 成功 | 谁先落终态谁赢；后者发现 rowcount=0 → 回收子进程 |
| 引擎跑完 vs 引擎超时被杀 | 同上，两边都收敛到合法终态 |
| guizang 自带 supervisor 判 timeout vs 调度器判 timeout | 调度器 deadline = 引擎超时 + 宽限，正常由引擎先落；调度器是**没有 supervisor 的引擎的兜底** |
| 两个调度器（多副本）抢同一行 | `claimed_by IS NULL` 的 CAS 保证只有一个赢 |

超时的所有权收归调度器统一按 `started_at + JOB_TIMEOUT + 宽限` 判定并调 `engine.cancel`，
于是"超时不杀进程"这个类别整体消失。

### 决策 5：引擎态到任务态的映射只存在一处，`cancelled` 不由引擎产出

调度器是唯一做映射的地方：`EngineJobStatus(4) → JobStatus(6)`。引擎永远不知道 `queued`/`cancelled`
存在（ADR-018 的分层枚举）。新增可选钩子 `cancel(job_id)`，能力位 `cancel` 按 `implements_hook()`
鸭子类型派生（与 `page_preview`、`prepare_runtime` 同族，遵守 ADR-001「不出现 `if engine_name ==`」）。
**不具备该能力的引擎对 running 任务撤回归 409，绝不静默"假撤销"**——契约已这么写。

### 决策 6：状态权威在 DB，不在内存，所以重启可自愈

调度器每拍从 DB 读 `status='running'` 的行重建跟踪集，不持有任何"只有我知道"的状态。
启动第一拍做收尸：pid 活 → 接管；pid 死有产物 → completed；pid 死无产物 → failed（把证据写进 `error`）。

已知残留：`run.log` 的流式写入线程会随重启消失，被接管的在跑子进程其日志停在上次尾巴——
如实接受，不做假补全。

### 决策 7：per-identity 粗闸取代加权调度

本期只做 FIFO（先来先服务），不做按用户公平轮转；改为在 `POST /api/decks` 上加一道粗闸：
**同一身份（登录用户 / 访客令牌）未完成任务数达上限即 409**，并同步进契约。
理由是加权调度要引入记账与优先级模型，而本期真正的风险只是"一个人把队排到 50 个"。

## 配置

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `DECKSMITH_MAX_CONCURRENT_JOBS` | **2** | 全局同时在跑的任务数。每条任务 = 一个几百 MB 的 claude Node 进程 + 网关配额，默认取保守值，按实测上调 |
| `DECKSMITH_MAX_UNFINISHED_PER_IDENTITY` | **10** | 单身份未完成任务（queued + running）上限，超了 409 |
| `DECKSMITH_SCHEDULER_INTERVAL` | 5 秒 | 调度节拍 |
| `DECKSMITH_JOB_TIMEOUT` | 3600 秒 | 沿用原 `_DEFAULT_TIMEOUT_SECONDS`，另加 120 秒宽限避免与引擎内 supervisor 抢判 |

默认 2 是**刻意保守**：第三方 Anthropic 兼容网关的实际配额我没有数据，不敢替现场定一个"看起来专业"的数。

## 后果

**收益**

1. 40 线程墙拆除：请求线程不再被任何长任务占用，`/api/version` 在 60 个任务排队时仍应毫秒级返回。
2. 并发第一次有了可配置、跨重启可见的上限；误提交与卡死任务第一次有出路（撤销）。
3. 重启不再产生幽灵 running；超时不再产生僵尸 claude 进程。
4. "非终态"从 7 处 `status !== 'running'` 的隐式假设变成一处显式判据。

**代价与风险**

1. **单进程假设被写进架构**：调度器是进程内线程。好在认领走 DB 层 CAS，多副本不会重复执行同一任务，
   所以是"降级安全"而非"禁止扩容"；真正挡着水平扩的仍是进程内 agent 会话/SSE 与无锁的 `job.json`。
2. `claimed_by` 两段式认领比"一把梭置 running"多一处失败分支（fork 后 CAS 输掉要回收子进程），
   写漏就是新僵尸。已列为单测必查项。
3. DB 加 3 个可空列（`claimed_by`/`claimed_at`/`started_at`），走 `_MIGRATIONS` 幂等补列、
   不升 `SCHEMA_VERSION`（按 `core/db.py` 既有规矩）。这三个字段**不进契约**，是编排层内部状态。
4. 硬缺失报错时机变化（决策 2）。
5. 本批只完成后端 + 引擎侧；前端那 7 处判据与 `StatusTag` 两键在下一批，
   期间 `tsc` 会有 1 个已知报错（ADR-018 落地时就已存在）。

**明确不在本批**

- 读路径 progress 落库（调度器每拍把 `stage`/`pages_generated` 写进 DB，替掉 `GET /api/jobs` 每 2 秒
  现扫盘、并在 GET 里写 `job.json`）——与调度器天然一对，但属下一批。
- `job.json` 原子写与跨实例锁。
- 产物归属去 mtime 化。
- `engine/core/models.py` 手写枚举的生成化与 CI 覆盖（本批只做改名同步）。

## 验收判据

1. stub 引擎灌 60 个任务后，`GET /api/version` P99 **< 50ms**（改前基线：约 36 个后为 29.5 秒）。
2. `MAX_CONCURRENT_JOBS=2` 且队列堆 20 个时，同时被 `status()` 判为 RUNNING 的任务数恒 ≤ 2。
3. 杀掉进程再起回来，DB 中不残留任何永久 `running`/`queued` 的行。
4. 撤销一个已被预留槽位但尚未 running 的任务，**不留下已 fork 却无人跟踪的子进程**。
5. 全量单测、契约测试、`check-alignment` 全绿。
