# ADR-020: 系统设置——DB 覆盖 env 的运行期配置面，schema 驱动渲染

- 状态: 已接受（已实现并验证）
- 日期: 2026-09-28
- 决策者: 龚成
- 相关: ADR-018（分层枚举）、ADR-019（调度循环与并发闸，本 ADR 把它的环境变量变成可调项）、
  `docs/contracts/openapi.yaml` 的 `/api/admin/settings` 与 `/api/settings/capacity`

## 背景

ADR-019 把并发闸做成了环境变量（`DECKSMITH_MAX_CONCURRENT_JOBS` 等）。这在开发期够用，
交付现场立刻撞墙：改一个闸门值要改 `.env` 并 `up -d --force-recreate` 重建容器，
而重建会打断正在跑的任务（虽然调度器首拍能收尸/接管，但代价是用户看到一轮"任务重启"）。
现场调参的频率远高于发版，不该走发布通道。

同时用户提出：要一个仅管理员可见的系统设置菜单，并且**后续还要放 agent CLI 的配置**——
所以这一层不能按"三个数字的表单"实现，必须是一次到位的扩展位。

仓库里已有两类配置面，边界必须先划清，否则同一个值会有两个来源互相不知道对方存在：

| 类别 | 载体 | 作用域 | 改动方式 |
|---|---|---|---|
| 部署配置 | 环境变量 / `.env` | 全实例 | 改文件 + 重建容器 |
| 个人偏好 | `user_settings` 表 | 单用户 | 界面即时保存（仅作初始值，不越权） |
| **系统设置（本 ADR）** | `system_settings` 表 | 全实例 | 界面即时保存，仅管理员 |

## 决策

### 决策 1：DB 覆盖 env，可"恢复默认"

env 提供**默认值**，`system_settings` 存**当前生效值**。有覆盖取覆盖，无覆盖取 env/内置默认。
管理员对某项提交 `null` 即删除覆盖、回落到 env。

不采用"env 定硬上限、DB 只能在上限内调"：那会让现场遇到"上限本来就不够但改不动"的死局，
而 env 本来就是运维自己写的，没有对抗性需要设防。

### 决策 2：生效语义按"读取时机"逐项声明，一律不谎报

调度器每拍读取生效值，所以并发闸、调度节拍、任务超时**改完对下一个任务立即生效、不需要重启**
（`restart_required=false`）。这个属性不是全局的，而是每项自己的事实——因此契约把它做成
字段级元数据，由设置页据此显示"已生效"或"需重启后生效"。

**明确禁止**"一律显示稍后生效"这种含糊话：管理员改完闸门看到"已生效"却在排队，
比看到"需重启"更破坏信任。

### 决策 3：agent 配置注入子进程 env，而不是改服务进程

后续 agent CLI 的配置（可执行文件路径、base url、token 等）由调度器在 `fork` 子进程时
注入**该子进程的环境变量**，不改本服务进程的状态。理由有三：

1. 改本进程 `os.environ` 会影响同进程内所有在途任务，且无法回滚；
2. 子进程继承式注入天然做到"下一个任务用新配置、在跑的任务不受干扰"；
3. 它是决策 2 里 `restart_required=false` 能成立的机制前提。

### 决策 4：schema 驱动渲染，前端零字段名

后端持有一张**设置项注册表**，每项带元数据（键名、分组、中文名、说明、类型、单位、上下限、
默认值、生效方式）。`GET /api/admin/settings` 返回元数据 + 生效值，前端一个通用渲染器按
`type` 出控件、按 `group` 分区。

这与引擎参数表单（`params_schema` 驱动、中文映射、条件显隐）是同一套原则，不是新发明。
**本期只交付 `scheduler` 分组**；`agent` 分组待用户明确要放哪些键时由注册表加项带出，
契约与前端均不需要改动——这就是"预留扩展性"的具体落点，而不是留一个空页面。

### 决策 5：secret 类型三项硬约束

面向 agent CLI 的 token 这类值，类型标 `secret`，并受三条约束（写进契约描述）：

1. `value` 恒为 `null`，明文**永不离开后端**；
2. 只回 `configured`（是否已配置）与 `masked`（形如 `sk-…3f9a`，供确认"是不是这一个"）；
3. 任何日志与错误信息不得落明文。

配套的边界：模型凭证与 agent CLI 的接入方式由用户本人配置，本系统只提供写入通道，
不主动代劳搬运密钥、不评价其鉴权方式。

### 决策 6：校验失败一律整次 400，不做部分成功

`PUT` 提交多键时，任一键不合法（越界、类型错、未知键）即整次 400 并逐项列出原因。
"部分成功"会让管理员以为改成了而实际没有，是更难排查的状态。未知键同样 400——
静默忽略等于把拼错的键名吞掉。

### 决策 7：给非管理员只开一个只读容量口子

设置页仅管理员可见（后端 `require_admin` 强制，前端隐藏只是体验）。但等待的用户有权知道
"为什么慢"，所以单独开 `GET /api/settings/capacity`，只返回三个数：
`max_concurrent_jobs / running / queued`。不暴露配置项清单、不暴露密钥状态。

界面落点是提交处的只读提示（不新增页面），与列表里已有的"前面还有 N 个任务"配合，
把"排队"这件事解释清楚。

> **后续修订（ADR-022，2026-09-30）**：本决策开的只读口子保留，但**界面落点已变更**——
> 顶部常驻容量横幅下线（它播报的是全系统负载，对单个用户是噪音，也是不必要的暴露面；
> 且全局闸从不拒提交、真正会拒的 per-identity 粗闸文案本就自解释）。"为什么要等"改由
> 排队任务的状态明细按需承载（队首区分"即将开始 / 等待空位（N 个正在生成）"）。
> `GET /api/settings/capacity` 与前端 `getCapacity()` 均保留，不因此删除。

## 后果

1. **多了一个配置真源**，读配置的地方必须统一走"取生效值"这一个入口，绝不能有的地方读 env、
   有的地方读表。实现时 `core/config.py` 的那四个 getter 要改成"表优先、env 兜底"，
   并保持调用点不变——这是本决策最容易做错的地方。
2. `system_settings` 一行一项（不是整包 JSON）：单项可审计、可单独回落、加项不改表。
   代价是表更"碎"，以及需要 `updated_by`/`updated_at` 记改动痕迹。
3. 改配置不再需要重建容器，ADR-019 的"现场调参要发版"这条限制解除。
4. 本期不实现 agent 分组，但机制（分组、类型、secret、子进程注入点）已定义在契约里；
   若后续 agent 配置项需要"重启才生效"的（例如换 CLI 版本），它必须如实标
   `restart_required=true`，而不是伪装成热生效。
5. 契约版本应随本批实现升到 0.10.0（新增端点与 schema 属能力扩张）。

## 契约层已改动清单

- `docs/contracts/openapi.yaml`：新增 `GET/PUT /api/admin/settings`、`GET /api/settings/capacity`
  三个端点，及 `SystemSettings` / `SystemSettingsField` / `SystemSettingsUpdate` / `CapacityInfo`
  四个 schema。
- `scripts/check-alignment.py`：接口映射补三条，纳入既有对齐校验。

## 实现与验证

实现落在 `core/settings_catalog.py`（注册表，唯一的设置项知识源）、
`core/runtime_settings.py`（生效值解析：表优先、env 兜底，表缺失/脏值一律退回默认并告警）、
`repository/settings.py`、`service/settings.py`、`api/admin_settings.py`；
调度器的 `max_concurrent / interval / timeout_seconds` 改成 **property 每拍重读**
（构造时显式传值仍可钉死，供测试与特殊部署）；提交粗闸同样读生效值。
前端 `SystemSettingsTab` 按 `fields[].type` 通用渲染、按 `groups[]` 分区，
**不写死任何一个键名**；`CapacityNotice` 挂在工作台顶部，自持 15 秒轮询。

真浏览器复验抓出并修掉两个只有"真去跑一遍"才会露的问题：

1. **env 与注册表各定各的边界**：启动时把 `DECKSMITH_MAX_UNFINISHED_PER_IDENTITY` 设成 500
   灌测试数据，设置页就显示出一个标红的 500，而输入框最大只能填 200——管理员一碰这个框
   反而把系统调严了。修法是 `SettingField.default_value()` 把 env 给的默认值夹回注册表
   声明的区间并告警，边界只留注册表一个真源。
2. 两处 antd 弃用告警（`Card bordered`、`InputNumber addonAfter`）由本页引入，改掉后
   dev 浮层的 issue 数从 3 降回 1（剩下那条是既有的 Modal `destroyOnClose`）。

另外自我纠正一处契约与承诺的自相矛盾：`SystemSettingsField.group` 原本写成固定枚举
`scheduler`，而本 ADR 承诺"加 agent 分组时契约与前端都不用改"——固定枚举使这句承诺不成立。
已改成普通字符串（分组清单由响应体的 `groups[]` 动态下发），并把"每个字段的分组必须真的
存在于 GROUPS"这条不变量移到后端单测里守。

验证数据：后端单测 183 passed（新增 `test_system_settings.py` 17 例，含热生效、脏值容错、
表缺失容错、校验整次失败、未知键拒绝、secret 明文不出接口、env 越界夹回、契约字段对齐）；
`check-alignment` exit 0；`tsc` 0 报错。
端到端热生效实测：同一进程、**不重启**，闸门 1 → 在跑 1 → 界面保存为 4 → 下一拍在跑 4 →
提交 `null` 恢复默认 → 回到 env 的 1；`/api/settings/capacity` 全程跟着变。
