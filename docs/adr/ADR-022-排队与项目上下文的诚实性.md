# ADR-022: 排队与项目上下文的诚实性——队首分说有无空位、容量提示退出常驻、身份变化作废项目绑定

- 状态: 已接受（已实现并验证）
- 日期: 2026-09-30
- 决策者: 龚成
- 相关: ADR-018（分层枚举）、ADR-019（并发闸）、ADR-020（系统设置与只读容量口子，
  **本 ADR 修订其决策 7 的界面落点**）、ADR-021（产物结构守卫，同期）；
  `docs/contracts/openapi.yaml` 的 `Job.status_detail`

## 背景

三件事同源于一个毛病：**界面上写了它兜不住的话**。

### 一、队首的"即将开始"是一句谎话

ADR-018 引入 `queue_position` 后，队首（前面没有未认领的排队者）统一渲染成"即将开始"。
实测现场：闸门 `max_concurrent_jobs=2`、2 个任务正在生成、第 3 个排第一 →
`queue_position=0` → 界面显示"排队中 · 即将开始"。可它**必须等某个 running 让出槽位**
才会开始，"即将开始"当时不可能成立。用户的第一反应就是"没看到排队位置"。

根因是口径本身：`queue_position` 只数**前面未认领的 queued 行**，不含占槽的 running。
这个口径当初是有意选的（数字要保守、不承诺精确等待量），但队首这个特例把它变成了
错误陈述——"前面没人"被写成了"马上轮到你"。

### 二、容量横幅不该常驻给所有用户

ADR-020 决策 7 开了 `GET /api/settings/capacity`，界面落点是工作台顶部常驻一行
"系统同时生成 2 个任务 · 当前 2 个在生成、2 个排队中"。三个问题：

1. 它播报的是**全系统**负载（含别人的任务），对单个用户是噪音；把"系统多忙、几个人在跑"
   摊给每个访客，也是不必要的暴露面。
2. 它唯一的实际价值是解释"为什么被拒"。但**全局并发闸从不拒提交（只排队）**，
   真正会拒的只有 per-identity 粗闸，而后端那句文案本来就自带解释：
   "你已有 N 个任务未结束，达到上限 M；请等待其中一个完成或先撤销"。
3. 位置上它压在内容区之上、与"当前项目"行抢视线。

### 三、退出登录后"当前项目"还绑着，提交必 404

现场复现（实测）：管理员在项目 `c4405da1…` 下工作 → 退出登录 → 工作台仍显示
"当前项目：工作包技术要求参考文件 c4405da1" → 点提交 → **HTTP 404「项目不存在」**
（`_ensure_project` 对无权访问的 project_id 按"不泄露存在性"回 404）。用户看到的现象是
"怎么点都生成不了"。

两条泄漏路径：

1. `currentProjectId` 是 `WorkspaceTab` 的组件内 state，**原地登录/退出不会重挂载**；
   而"当前项目不在可见列表就置空"这条自愈规则只在 `refreshProjects()` 里，
   它只在挂载和提交后被调用，身份变化时没人叫它。
2. page 级还有个 `workspaceProjectId`（从历史项目「操作」跳入时赋值），
   **从来没人把它清回 null**；`WorkspaceTab` 靠 `key` 重挂载重置时，又把它当
   `initialProjectId` 塞回去。所以"切走再切回"也救不了这条。

## 决策

### 决策 1：队首按"有无空位"分说，排在后面不变

`_queued_status_detail` 增加占位事实（`running` / `capacity`），队首分两支：

| 情形 | 文案 |
|---|---|
| 前面有 N 个排队者 | 排队中 · 前方还有 N 个任务 |
| 队首 **且** running < capacity | 排队中 · 即将开始 |
| 队首 **但** running ≥ capacity | 排队中 · 等待空位（N 个正在生成） |
| 位序取不到 | 排队中（退回静态案，绝不编数字） |

`queue_position` 的口径**不改**（仍只数未认领排队者，契约字段语义不变）——改的是
队首那句话的诚实度，不是数字的定义。占位查询只在 `queue_position == 0` 时才发生，
排在后面时用不上，不白查两次。

### 决策 2：这句话只有一个作者（后端），前端只去前缀

"有没有空位"的事实（running 数 + 闸门值）全在后端。前端要自己判，就得再拉一次
`/api/settings/capacity`，于是同一句话有了两个作者、迟早漂移。所以后端把完整句子
写进 `status_detail`，前端新增 `queueDetailLabel()` **只负责去掉与旁边「排队中」状态
标签重复的前缀**，取不到才退回 `queuePositionLabel()`。详情抽屉正文里那句
"任务在排队，前方还有 N 个任务，尚未开始生成"随之删掉位置子句——上方「状态明细」
已经说了，同一事实不在一处说两遍。

### 决策 3：容量横幅下线，端点与 api 客户端保留

删除 `CapacityNotice.tsx` 及其在工作台的渲染。**保留** `GET /api/settings/capacity`
与前端 `getCapacity()`：契约里登记的只读 API 不因 SPA 暂时不调用而变废，
管理员侧/未来界面仍可消费。这是对 ADR-020 决策 7 的**部分修订**：口子照开，
界面落点从"提交处常驻提示"改为"排队文案按需承载"。

### 决策 4：身份变化即作废项目绑定，两处各堵一条路径

- `WorkspaceTab` 订阅身份（`user_id` 与 `visitorId` 合成 key），变化时调
  `refreshProjects()` → 复用既有的"不在可见列表就置空"规则，**不另写第二套清空逻辑**；
  挂载那一次由初始化 effect 负责，用 ref 跳过，避免同一件事拉两遍。
- `page.tsx` 在同一身份 key 变化时把 `workspaceProjectId` 清回 null，堵住
  "重挂载又把旧绑定塞回来"这条回灌路径。
- 兜底：创建向导提交撞到 404 且当时带着 project_id 时，提示"当前项目已失效，
  已切回新建——请重新提交"并清空选中，而不是把 404 原文甩给用户
  （那句话用户读不懂，且他会对着同一个死项目反复点）。

## 后果

1. 排队文案不再承诺它兜不住的事；闸满时用户看到的是"等待空位（2 个正在生成）"。
2. 工作台少一条常驻全局负载横幅；解释"为什么被拒"的职责交回给 per-identity 那句
   本来就自解释的 409 文案。
3. 退出登录后当前项目自动清空，可直接新建；历史跳入的绑定不会跨身份存活。
4. **代价**：队首多两次只读查询（running 计数 + 闸门生效值），仅在 `queue_position==0`
   时发生；`refreshProjects()` 在身份变化时多一次列表请求。都可忽略。
5. **已知边界**：`queue_position` 仍不含 running，所以"前方还有 3 个任务"在闸满时
   依然是保守数（真实要等 3+占位数）。本 ADR 只修队首那个特例的谎，不改全局口径——
   改成合并口径会让"前面"这个词失去直觉含义（当初正是因此否掉的）。
6. `getCapacity()` 目前前端无消费者，属有意保留（见决策 3），不是遗漏。

## 验证

- 后端 `test_scheduler.py` 新增 4 条：队首有无空位的文案矩阵（纯函数）、
  闸满走完整出参链路、有空位走完整出参链路、（原有）重试探针保留语义。
  backend 119 / engine 54 / contract 34 全过，`check-alignment` 通过，`tsc --noEmit` 干净。
- 契约 `Job.status_detail` 与 `getJob` 描述补上队首两分支语义。
- 真浏览器复验：闸满时列表标签与状态明细、原地退出后"当前项目"回到未关联且能新建。
- 同期教训（已修）：ADR-021 的"真实案例回归锚"原先断言"产物里没有 nav"，
  而该产物已被守卫修好——夹具前提被自己的修复动作消灭。改为**从真实文件反向造缺陷**
  （删一行再让守卫补回，并断言逐字节还原完好态），从此不依赖文件恰好是坏的。
