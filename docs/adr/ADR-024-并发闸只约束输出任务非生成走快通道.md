# ADR-024: 并发闸只约束输出引擎任务——草稿/修改走独立快通道，不占生成槽

- 状态: 已接受（决策先定；调度器实现落 package 层，随 ADR-023 改造一并做）
- 日期: 2026-10-05
- 决策者: 龚成
- 相关: ADR-019（任务调度循环与并发闸——本 ADR 收窄其适用面）、ADR-022（排队与队首文案）、
  ADR-023（pptmaster 逐页修改，修改任务因此**不进**生成排队闸）；
  `docs/contracts/openapi.yaml` 的 `JobStatus`/`Job.queue_position`；`docs/vc_design/states/01`

## 背景

ADR-019 立了一条专职调度线程 + `max_concurrent_jobs` 并发闸：`_claim_queued` 用
`slots = max_concurrent - count(status=running)` 认领 `queued` 行。问题是**这条认领不看 `task_type`**——
今天所有任务（草稿引擎任务、输出引擎任务）都挤在同一条 FIFO、共抢同一批 `max_concurrent` 生成槽。

后果（用户口径的"影响所有任务"）：

- 一堆本该秒级的 `source_to_md` 草稿转换会占住昂贵生成槽，把真正的 PPT 生成挤到排队；
- 反之亦然，轻重不分、一条队列互相拖累。

并发闸的**本意**是约束"会 fork 重进程（claude）、分钟级"的生成负载，不是给所有任务设的路障。

## 决策

### 决策 1：只有输出引擎任务进"生成排队 + 并发闸"

`max_concurrent_jobs` 只用来约束 `task_type = output` 的生成任务。认领时只从
"output 且 queued"里取、`running` 计数也只数 output——草稿/修改任务不再占生成槽、
不再排在这条队后面。

### 决策 2：草稿、修改任务走独立快通道，仍异步、不占生成槽

- 非 output 的任务在一条**独立的轻量执行通道**上跑：仍是后台异步，**不回到请求线程、
  不用 `BackgroundTasks` 与同步路由共用 anyio 池**（那正是 ADR-019 要避免的 ~36 并发冻结）。
- 它不消耗 `max_concurrent_jobs`，所以生成再忙也不会把草稿转换/重导出堵死，反之草稿再多
  也不挤生成。
- **仍受 per-identity 未结束上限兜底**（ADR-019 决策 7）：快通道任务照样计入"该身份未结束任务数"，
  防单个身份把快通道灌满。粗闸口径从"queued + running"调整为覆盖两条通道的未结束集合。

### 决策 3：契约可见影响

- `JobStatus` 的 `queued` 语义收窄为**只对输出引擎任务成立**：草稿/修改任务提交后直接进
  `running`（快通道立即认领），一般不会观察到 `queued`。终态集合不变。
- `queue_position`（队首位序）只对输出任务有意义；非 output 任务该字段为 `null`（它不在这条队里）。
- 队首文案（ADR-022）只对输出任务的排队成立，快通道任务不渲染"排队中/前方还有 N 个"。

## 后果

1. 轻重负载解耦：昂贵的 PPT 生成不再被秒级草稿/重导出挤占，快通道任务也不必排生成队。
2. 不破坏 ADR-019 的初衷：快通道仍异步、不碰请求线程池；per-identity 粗闸仍防灌水。
3. 前端要按"该任务是不是输出任务"决定是否显示排队位序，不能假设所有任务都会 queued。
4. **已知边界**：对话式修改会 fork claude（重进程），但按本决策它属"修改任务"、走快通道、
   **不受 `max_concurrent` 约束**——理论上可并发拉起多个 claude 改稿进程。MVP 可接受，
   由 per-identity 未结束上限兜底；若后续要限重进程，另立 ADR 把"按是否会 fork claude 判定"
   升级进来（当初评估过的备选口径），不在本 ADR 展开。

## 层三实现点（随 ADR-023 改造落地，本 ADR 不写码）

- `repository/jobs.py`：`claim_next_queued` 加 `task_type == 'output'` 过滤；`count_by_status`
  供生成闸只数 output；`count_unfinished_for_identity` 覆盖两条通道的未结束集合。
- `service/scheduler.py`：生成闸按 output 计槽；另起一个轻量执行体（独立线程/小池，自带较小上限）
  跑非 output 的 queued→running，不经 `max_concurrent`。认领、轮询、终态落库沿用既有 CAS。
- 契约：`JobStatus`、`Job.queue_position` 描述补"仅输出引擎任务会排队/有位序"。
