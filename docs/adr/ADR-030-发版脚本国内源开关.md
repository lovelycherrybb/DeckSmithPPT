# ADR-030: 发版脚本加国内源开关（默认官方源，`--mirror cn` 切换）

- 状态: 已接受
- 日期: 2026-10-21
- 决策者: 龚成
- 相关: ADR-012（交付形态）、ADR-026（假绿灯改真检查）、ADR-014（上游技能版本唯一源）；
  实测记录 `docs/research/2026-10-21-v0.6.1交付包产出记录.md`、
  `docs/research/2026-10-16-v0.6.0交付包出包记录.md`

## 背景

出 0.6.2 的 amd64 包时，在一台 x86 原生构建机上连续撞墙，两处都与代码无关，是"从哪儿取包"：

1. `apt-get` 连不上 `deb.debian.org`（负载 0.03、十分钟不动；同期测清华源 1 秒返回）；
2. `pip install` 下到一个 68.9MB 的轮子时读超时中断。

这台机器不是个例。0.6.0 那次原生构建就已经把基础镜像指向国内加速节点（`docker.m.daocloud.io`），
只是 apt 与 pip 当时勉强能通。也就是说，境内机器从官方源构建这件事本来就不可靠，只是此前
没被写进流程，全靠临场变通。

我这次的临场变通本身是有害的做法：临时造了一个"换好源的基础镜像"再传 `BASE_IMAGE` 进去。
它能出包，但产物与官方路径构建出来的包在**取证上**说不清——出厂清单里没有任何一处记录过
"这台包是换源构建的"。这类含糊正是 0.6.0 出包记录里已经踩过的那类问题。

## 决策

一、**发版脚本提供一个开关**：`bash scripts/release.sh <版本> --mirror cn`（等价于
`MIRROR=cn`）。只认两个值：不给或 `official` 走官方源；`cn` 走国内镜像。其他值当场报错退出，
不许"看着像拼错了就当默认值"。

二、**默认路径逐字不变**。不传开关时，脚本传给构建器的取包地址参数全为空，而空值等于
Dockerfile 里的默认值，等价于"一行源都不改、一个额外参数都不加"。这条由
`tests/contract/release_mirror_switch_test.py` 钉住，不靠人记。

三、**换源范围只到"从哪儿取包"**，不改"取哪些包"：

| 通道 | `cn` 模式指向 | 说明 |
|---|---|---|
| apt | 清华 Debian 与 debian-security | 走 http：实测该机构建环境的加密流量被网络侧换过证书，容器里 apt 验不过 https 的证书链；apt 索引自带签名校验，退 http 不降低完整性保证 |
| pip | 阿里 PyPI 为首选，清华降为备用索引（2026-10-26 修订，理由见"六"） | 版本仍由 `requirements.txt` 钉死，镜像站只改取包地址 |
| npm | npmmirror | 同上，`package-lock.json` 与 claude CLI 版本断言都不放宽 |

四、**换源这件事必须留在产物上**，两处留痕：镜像标签 `decksmith.build-mirror`
（`docker inspect` 当场可查），以及出厂清单 `MANIFEST.txt` 的"取包源"一行。事后任何人拿到
一张包，都能不靠回忆地判断它是从哪条路构建的。

五、**补一个试跑模式** `RELEASE_DRY_RUN=1`：只打印将要执行的构建命令，且把产物目录指到临时
目录。加这一条有两个原因——让上面那条检查件能在两秒内跑完；以及本脚本会**整体重写**
`dist/SHA256SUMS` 与 `MANIFEST.txt`，这个行为已经造成过两次旧版本出厂清单丢失
（2026-10-16、2026-10-21），不能再多一次。

六、**2026-10-26 修订：pip 首选源换成阿里，并给三处取包挂持久缓存**。出 0.6.3 时同一台
x86 构建机上第五次失败才查到根因——清华 PyPI 当时只有约 135 KB/s，一个 79KB 的包下了
137 秒仍中途断流，四十分钟的构建毁在这一步。同机同网络路径实测六个源：

| 镜像站 | 实测吞吐 |
|---|---|
| 清华（原首选） | 约 135 KB/s |
| 阿里 | 约 1.9 MB/s |
| 南大 | 约 0.95 MB/s |
| 华为 | 约 0.75 MB/s |
| 腾讯 | 约 0.42 MB/s |
| 中科大 | 301 跳转，未直用 |

换源只改地址，依赖清单与钉住的版本一字未动（本 ADR 第三条不变）。同时给两个 Dockerfile
的 apt / pip / npm 三处取包挂上 BuildKit 持久缓存（`--mount=type=cache`）：过去一次失败
会把约 1.5GB 依赖从头再下，挂上之后重试只补没下完的那几个。缓存目录是挂载点，**不进镜像
层**，交付包内容与不加挂载时一致。配套检查件 `tests/contract/build_cache_test.py` 守住
两件事：三处挂载都还在；以及不许再出现把缓存清回去的写法——本次就先犯了这一条，后端
原有的 `PIP_NO_CACHE_DIR=1` 与 `npm cache clean --force` 作用正是"下完就扔"，与挂载互相
抵消，已随本次一并去掉。

## 后果

好处：境内机器出包从"临场变通"变成"一条参数"，产物可核对；检查件守住默认不变。

代价与风险，如实列出：

1. 镜像站是官方源的副本，存在同步滞后与个别文件缺失的可能。缓解手段是 pip 保留清华作
   备用索引、npm 与 claude CLI 有版本钉死与构建期断言；apt 侧没有等价兜底，若某包在镜像站
   取不到，仍须回到官方源构建。
2. "换源构建"与"官方源构建"的两张包不承诺逐字节一致（依赖内容相同，构建时间与文件顺序
   等元数据本就不同）。因此第 4 条留痕不是可选项。
3. 本次不做的事：不把国内源设为默认，不改任何依赖清单与钉住的版本，不改基础镜像默认地址
   （仍由 `BASE_IMAGE` 自行指定加速器）。

## 验证状态

- 检查件四条断言在本机通过（默认不变、cn 全通道非空、未知值报错、试跑不碰真出厂清单）。
- **`cn` 模式已完成真实构建与真机运行验证（2026-10-22，x86 原生构建机）**：
  `PLATFORMS=linux/amd64 bash scripts/release.sh 0.6.2 --mirror cn` 退出码 0，产出两张包
  （app 803,586,999 字节 `2f0db511…eb2d6`、web 97,392,343 字节 `4fa4668d…fcd6`）；包内核验
  `os/architecture` 确为 `linux/amd64`，镜像标签 `decksmith.build-mirror` 确为 `cn`，
  出厂清单"取包源"一行如实记录为国内镜像。
- 同一批包在该 x86 机器上完成一次起服务验证：导入成功，`docker compose up -d --no-build`
  后后端 healthy、界面 5 秒内就绪，五个引擎的启动预检逐条"前置条件就绪"，
  经界面打到后端的引擎清单返回 5 个、版本接口回报 `0.6.2`。
- 边界仍要说明：该次起服务**未配模型凭证**，因此"上传材料→真实出片"这一环**没有验证**
  （部署指南把这一步列为完整验收的必要项）。amd64 的生成链路端到端出片仍是未了项，
  需带真实凭证跑一次才算结清。
